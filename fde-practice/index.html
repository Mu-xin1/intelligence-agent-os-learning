DAY 01追踪一次“确认经历”

约 120 分钟

把页面操作与真实数据变化对应起来。

01先理解 · 20 分钟

一次操作通常经过页面事件、HTTP 请求、路由校验、业务处理和存储。页面显示成功只是其中一步，需要检查数据是否真的保存。

Job Agent 的 CareerClaim 是个人经历证据。今天只追踪一条经历由待确认变为 confirmed 的路径；先用测试数据，记录当前代码版本。

02动手做 · 80 分钟
  1. 启动现有项目，创建或选取一条测试经历；记录操作前的状态。
  2. 打开浏览器 Network，点击确认，记录请求方法、地址、请求体、响应码及响应体。
  3. 从 Claims.tsx、api.ts 追到后端 routes.py、service.py、storage.py，写出实际函数名；文件位置以当前版本为准。
  4. 核对存储结果并刷新页面，画出五层链路，标明每层的输入、输出与责任。
故障与边界练习输入一个不存在的经历 ID，观察错误由哪层产生；记录错误码与页面提示。不要把这次失败算成确认成功。

接口返回成功，但刷新后状态没变化，应先查什么？

先比对请求中的 workspace 和经历 ID、实际响应体与数据库记录，再检查事务提交、读取路径和前端缓存。按证据逐层缩小范围，不能仅凭成功提示判断。

DAY 02把业务规则变成断言

约 120 分钟

知道哪些行为必须稳定，哪些行为需要进一步确认。

01先理解 · 20 分钟

断言是明确的预期，例如“未确认的经历不能被选作已确认事实”。断言应来自业务约束，再去核对实现。

幂等意味着同一操作重复执行时，不应产生意外的额外业务效果。状态、版本号与下游更新是否应该变化，需要分别定义。

02动手做 · 80 分钟
  1. 沿用昨天的测试数据，写出确认、重复确认、撤销确认三种预期。
  2. 检查确认状态如何影响岗位匹配、证据选择和已有材料；区分已有材料与重新生成的材料。
  3. 使用现有测试结构，为正常路径与非法输入补充必要断言；若已覆盖，解释现有断言。
  4. 运行相关测试并检查数据，记录任何“文档预期与实现不一致”的地方。
故障与边界练习撤销一条经历的确认状态后再生成材料，检查是否仍引用它。若旧材料仍保留引用，明确历史留存与新生成的规则。

DAY 03完成一个可验收的小改动

约 120 分钟

练习从需求到实现，再到验证的完整过程。

01先理解 · 20 分钟

先写触发条件、期望行为与失败处理，再决定修改哪些层。小需求也需要让用户能判断结果。

本次建议检查材料生成来源：规则生成、模型润色、模型异常后回退。若当前版本已经具备，补齐缺失的提示或失败场景验证。

02动手做 · 80 分钟
  1. 写一张需求卡：用户什么时候需要知道来源，界面显示什么，失败时保留什么。
  2. 列出需要修改的接口字段、业务逻辑和显示位置，先让 AI 审查计划。
  3. 实现最小改动，检查新增字段的兼容性；不要为一个提示重构整套架构。
  4. 对规则生成、模型成功、模型失败分别验证，保存差异和结果。
故障与边界练习模拟模型失败，检查是否错误显示为模型成功；同时确认回退材料仍可查看。

DAY 04稳定复现三类故障

约 120 分钟

从“偶尔出错”走到可复现、可定位、可验证。

01先理解 · 20 分钟

Mock 是用可控替身代替外部依赖。例如让模型接口固定超时，便能重复验证回退逻辑。它验证异常处理，不能评价真实模型质量。

日志需要帮助连接一次操作的各个阶段：请求、任务、依赖调用、最终状态。避免只留下没有上下文的“失败了”。

02动手做 · 80 分钟
  1. 选择模型超时、模型返回格式错误、经历 ID 不存在三种故障，分别写出预期。
  2. 用测试替身或受控输入触发故障，记录触发步骤与最小复现数据。
  3. 沿日志判断失败发生在哪层，核对页面提示、存储状态和回退结果。
  4. 选一个处理不完整的点修复，再运行正常路径与相同故障场景。
故障与边界练习移除一条关键日志，尝试重新定位同一故障，判断缺失了什么上下文，再恢复日志。

DAY 05第一周验收：解释、修改、排错

约 120 分钟

用操作和证据检验系统掌控程度。

01先理解 · 20 分钟

系统掌控能力可以通过一个受控挑战检验：先解释链路，再处理一个小变更，最后定位一类故障。可以使用 AI，但需要亲自判断和验证。

复盘关注决策依据：为什么改这里、排除了哪些原因、还有哪些情况没有测。

02动手做 · 80 分钟

  3. 完成修改或说明现有实现已满足的证据；复跑相关验证。
  4. 把一次排错写成“现象 → 假设 → 证据 → 修复 → 复测”，记录需要继续练的部分。
故障与边界练习复现本周最难的故障。如果仍只能照着答案操作，回到对应课程再练一次。

DAY 06定义什么才算“生成得好”

约 120 分钟

把笼统的质量要求转成可判断的标准。

01先理解 · 20 分钟

规则回归检查确定性的业务行为；模型评测检查真实输入下输出质量与波动。两者都需要，分别记录结果。

本轮主要问题是：相同岗位与证据下，模型润色是否让材料更贴合岗位、减少人工修改，同时保留事实？引用编号正确只是格式与来源检查的一部分。

02动手做 · 80 分钟
  1. 限定评测对象为一段岗位申请材料，固定输入格式：岗位要求、已确认经历、允许使用的事实。
  2. 先写评分表：证据是否相关、事实是否有依据、表达是否可用、运行代价如何。
  3. 用 3 个开发案例试评分。可用性采用 0/1/2：不可用、需大改、仅需小改；每档写一条例子。
  4. 提前定义失败：编造职责或数字算事实错误；超时、格式错误和回退单独计数。记录预期，但不预填结果。
故障与边界练习构造“引用编号存在，但文本增加了不存在的业绩数字”的例子。检查评分表是否能明确判错。

DAY 07整理 20 个评测案例

约 120 分钟

让评测覆盖容易失败的场景，并保留独立验证样本。

01先理解 · 20 分钟

每个案例需要可核查的参照：输入、相关证据 ID、允许表达的事实、不允许推断的内容，以及预期行为。参照答案可以是事实清单，无需唯一标准文案。

开发集用来发现问题与调整方案；留出集用于冻结方案后的验证。相同经历换几个说法的近似样本，应放在同一组，避免泄漏。

02动手做 · 80 分钟
  1. 构建 20 个案例，覆盖正常匹配、经历不足、否定表达、中英文术语、数字夸大等情况。优先使用人工可核对的测试材料。
  2. 每条保存 case_id、场景类型、岗位、经历证据、期望证据 ID、允许事实和禁止推断。
  3. 按案例家族分成 12 个开发样本和 8 个留出样本，尽量让两组都包含关键难例；今天的试评分样本归入开发集。
  4. 逐条人工核对事实标签，保存版本和分组，之后不要用留出集反复调提示词。
故障与边界练习示例：经历只写“参与供应商协作方案讨论”，模型却写“独立上线供应商平台”。参照应明确禁止推断“独立”和“上线”。

DAY 08运行规则与模型的配对比较

约 120 分钟

保留完整结果，让两种方案能够公平比较。

01先理解 · 20 分钟

配对比较意味着同一个案例在两种方案下运行。本轮固定岗位、证据和规则草稿，只改变是否做模型润色；它主要衡量润色的增益。

证据检索可以先与标注证据单独核对。如果想证明检索策略改善，需要另做固定生成条件的检索对照，不能从润色对比推断。

02动手做 · 80 分钟
  1. 写一个批量运行脚本，先跑 12 个开发案例，分别得到规则输出与真实模型润色输出。
  2. 记录 case_id、代码版本、提示词版本、模型配置、检索证据、完整输出、耗时和状态；能获得时记录 Token 用量。
  3. 模型方案每个案例运行两次，给每次运行独立编号；统计时保留重复运行的关联。
  4. 按评分表人工检查输出。超时、格式错误和回退都进入总表，不删除失败样本；费用仅在有真实计价依据时记录。
故障与边界练习故意让一次模型调用失败，确认脚本仍保存失败记录并继续后续案例；它不应被计为一次成功的模型润色。

DAY 09围绕一个主要错误做改进

约 120 分钟

找到错误根因，验证改动是否针对问题。

01先理解 · 20 分钟

材料错误可能来自事实数据、证据选择、提示词、生成或后处理。先定位错误在哪一层引入，再决定改哪里。

结构校验能检查字段与类型；引用校验能检查来源 ID；事实支持需要进一步核对语义。限制新增数字可帮助减少一类错误，但不能覆盖所有事实夸大。

02动手做 · 80 分钟
